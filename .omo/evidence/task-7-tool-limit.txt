Task 7 — Orchestrator Service: Tool call limit enforcement
============================================================

Date: 2026-06-10
Related: Sprint 3, FR-03 (Tool Execution), max_tool_calls_per_turn (settings.py:65-67)

Input
-----
- Message: "Why was I charged twice?"
- Customer ID: _TEST_CUSTOMER_ID (constant)
- Intent: "billing_inquiry" (confidence 0.92)
- Selected tools: ["get_billing_history", "get_support_tickets", "search_documentation"]
- Max tool calls: 2 (overridden from default 6)

Turn execution
--------------
1. IntentAnalyzer.analyze() returns all 3 candidate tools
2. ToolSelector.select() returns all 3 in selection plan
3. _execute_tools() iterates but only calls 2 tools:
   - get_billing_history → called (count: 1)
   - get_support_tickets → called (count: 2, limit reached)
   - search_documentation → NOT called (limit_exceeded → ToolResult.fail("Tool call limit exceeded"))
4. EvidenceAggregator receives results from only the 2 executed tools + 1 failure

Design rationale
----------------
- The orchestrator tracks a counter inside _execute_tools()
- Before each tool call, the counter is checked against max_tool_calls
- When exceeded, remaining tools get ToolResult.fail("Tool call limit exceeded")
- This avoids wasted API calls and respects the configured limit
- Even bypassing ToolSelector's cap doesn't help — the orchestrator enforces its own limit
- The limit is configured globally but can be overridden per-turn by ToolSelector's max_tool_calls

Validation
----------
- Test: test_only_max_tools_executed — monkeypatches ToolSelector to return 3 tools, sets max_tool_calls=2
- Asserts: only 2 tools actually called (via spy assertion), 3rd tool never invoked
- Tool functions receive correct kwargs for the tools that are called
- search_documentation receives ToolResult.fail() with "Tool call limit exceeded"
