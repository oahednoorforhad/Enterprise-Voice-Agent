[✓] 2. Mockable LLM client boundary
     File: app/core/llm_client.py
     - LLMClient class with injectable `client` parameter for test DI
     - `generate()` and `generate_structured()` async methods
     - LLMClientError wrapping SDK errors; consumers never import google.genai.errors
     - Tests pass LLMClient(api_key="sk-test", client=fake_sdk) — no real API keys needed

[✓] 3. Hard limit on tool calls per turn using max_tool_calls_per_turn
     - ToolSelector.__init__() reads settings.max_tool_calls_per_turn (default 6)
     - OrchestratorService.process_turn() slices plan.selected_tools[:plan.max_tool_calls]
     - ToolSelector enforces intent-specific caps (billing=4, support_ticket=3, etc.) min() with global cap
     - Low-confidence (< 0.3) further caps at 1 tool

[✓] 4. Partial tool-failure handling with graceful continuation
     - EvidenceAggregator collects failed tools in failed_tools list; does not abort on failure
     - OrchestratorService catches DomainException and generic Exception → ToolResult.fail()
     - EvidencePackage tracks both items (successful) and failed_tools separately
     - Reasoning pipeline receives both successful evidence and failed tools list in prompt

[✓] 5. Evidence-backed response generation only
     - ReasoningPipeline has two paths:
       (a) Insufficient evidence (no items) → deterministic fallback, NO LLM call
       (b) Evidence present → LLM with system prompt: "You must ONLY use the evidence below"
     - Greeting/other intents: deterministic friendly response (with name personalisation)
     - Non-greeting empty evidence: "I do not have enough information…" fallback
     - Confidence clamping to [0.0, 1.0]; invalid reasoning_type falls back to evidence_corroboration

[✓] 6. TDD-based pytest coverage
     - tests/test_orchestrator.py (922 lines, 16 tests) — full turn, greeting, partial failure, tool limit, unknown tool, sub-component calls, error propagation, output shape
     - tests/test_reasoning_pipeline.py (737 lines, 25 tests) — insufficient evidence, greeting, evidence-backed, confidence clamping, reasoning type validation, error propagation, output shape
     - tests/test_chat_api.py (232 lines, 7 tests) — happy path, greeting, customer context merging, validation rejects (3 tests), orchestrator construction

[✓] 7. Minimal POST /api/v1/chat integration point
     - app/api/chat_router.py: POST /api/v1/chat/ (prefix="/api/v1/chat")

     - Wired into app/main.py via app.include_router(chat_router)
